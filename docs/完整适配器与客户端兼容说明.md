# 完整 adapter 与客户端兼容说明

本文描述韩国飞行射击游戏 **Nanaimo** 的本地兼容链路。运行输入由使用者从合法取得的客户端副本准备；仓库提供 adapter、启动器、派生工具与兼容性数据。原始文件备份和哈希用于本机恢复与诊断。

## 1. 完整 adapter 结构

GUI 只启动一套完整 adapter：

```text
Nanaimo.Adapter.exe
  ├─ 登录、角色、村庄、社交、任务、商城、公寓、交易、竞技与娱乐
  └─ nanaimo_gameplay_bridge.exe
       └─ 地宫房间、战斗、首领、掉落、结算与原生状态交换
```

`Nanaimo.Adapter.exe` 监听客户端固定入口 `11005/11999/12050`；桥接进程使用单独的本机端口，不直接暴露给 GUI。运行状态位于 `adapter_data/`，日志位于 `adapter_data/logs/`。

GUI 的 **“一键进入 Nanaimo”** 会按顺序：

1. 停止当前完整 adapter 及桥接进程；
2. 保存角色配置和本地库存；
3. 确认 `game.exe` 存在，并调用 `scripts/prepare_client_compatibility.py --furniture --dungeon7 --overwrite --apply`；默认流程对已知 PE 布局应用五字节家具 Index 重定向并派生资源，emotion 代码保持原样；
4. 从使用者自己的文件生成本地覆盖，原子应用家具 Index 重定向、P03 道路及 SSTG/PON 别名并逐项复核；适配器通过固定 C393 快照契约提供场景对象，本地 getter 处理家具点击路径；
5. 将原文件按内容 SHA-256 备份到 `adapter_data/client_compatibility_overlay/backups/`；哈希作为本机备份与诊断指纹；
6. 启动完整 adapter，并等待 `11005/11999/12050` 全部可连接；
7. 经 `11999` 注册角色资料；
8. 只在兼容报告 `verification.all_pass=true` 后启动 `game.exe`。
## 2. 家具边界：C393 快照与 Index getter 分离

C393 家具快照采用统一布局：**1012 字节 payload、1020 字节完整帧、`payload+0` 对象数、`payload+2` 写入 WORD 2000、`payload+4` 起最多 84 条 12 字节普通家具记录、未使用区域清零**。地板和墙壁由 C38E/C424 承载。C393 负责有界场景快照，本地 Index getter 负责家具点击路径。

启动器选择 `--furniture --dungeon7`：PE 布局和当前五字节精确匹配时应用家具 Index-getter redirect，同时派生资源；emotion 代码保持原样。站点不匹配时工具保持输入文件不变并报告校验失败。

### 2.1 C393精确布局

```text
完整帧长度  1020
payload长度  1012
frame+8      WORD count
frame+10     WORD info/final = 2000
frame+12     第1条12字节对象记录
最大记录数   84
```

客户端在 `frame+10 == 6000` 时再次发送 C392；`0`、`2000` 及其他非 6000 值结束分页。适配器以 `2000` 表示完整快照终态。记录循环按 `count` 消费，紧凑的 `12+12*count` 完整帧覆盖静态读取；固定 1020 字节与清零尾部提供容量边界。家具点击随后进入独立的受保护 Index getter。

### 2.2 客户端兼容边界

一键流程以当前 `game.exe` 为输入，在确认 PE 布局和目标五字节后应用家具站点重定向：

```text
VA 0x0041235F
E9 9C C3 1B 00 -> E9 7C CC 1B 00
```

五字节或 PE 布局不匹配时，工具保持文件不变。该重定向把受保护入口 `0x5CE700` 指向现有的直接 Index getter `0x5CEFE0`；表情协议边界由 C355 独立承载。

### 2.3 验收顺序

1. 进入自己的公寓，确认只收到一个C393/1020完整快照；
2. 分别测试空房间、1件和多件家具；
3. 打开装修界面，点击、摆放、保存、取下家具；
4. 关闭并重新打开装修界面；
5. 退出公寓并重进，确认布局仍在；
6. 记录客户端进程、异常地址、C392/C393/C411顺序和FIN/RST。

静态链表明家具点击在 C411 提交前进入 `0x41235F -> 0x5CE700 -> ... -> 0x1011A51` 的保护器查找；C393 的长度、尾部和终态字段属于独立快照路径。工具报告站点匹配并应用重定向后，仍以原客户端可见操作作为最终验收。

### 2.4 表情翻页的适配器端协议边界

正式启动器保持 `VA 0x00837220..0x00837263` 的 emotion 代码不变。`C354/8 -> C355/728` 的适配器端构造以打包状态1（字节 `0x55`）填充完整帧 `+0x88..<+0xDF`；所有进度写入严格止于 `+0xDE`；`+0xDF..+0xEF` 是17字节情侣姓名，`WORD+0xF0` 是戒指后缀。无有效情侣关系时两者保持全零，原生姓名门控在戒指资源查找前关闭；只有目录中有效的 `43,000,000+N` 情侣戒指才会与非空姓名一起下发。

## 3. 拉米诺斯村地宫7兼容链
拉米诺斯村地宫7入口由五个边界共同构成：C355 前置进度、村庄道路、关卡资源命名、adapter 资源映射和嵌套 PON。原客户端读取 C355 `+0x80..+0x87`，并对 `k=0..21` 的每项要求两个 bit 同时为 `1`。静态链为：C355 分派 `0x0052C100` → 状态构造 `0x00544000` → 前置字段写入 `0x0054EDD0`；移动流程 `0x005000A0` → 前置判定 `0x00509EC0`，逐项检查 `+0x48` 的 bit `2*k` 与 `2*k+1`。

### 兼容链配置

1. 使用自己的合法客户端副本，并确认适配器在登录后重新发送完整 C355 帧。
2. 在 `release/components/dungeon_unlock/unlock_patch.inc` 的最终 C355 构造阶段写入低 44 个前置位：`C355 +0x80..+0x87 = FF FF FF FF FF 0F 00 00`。保留 bit44..63、`+0xC8` 显示域和其他字段；仍由 C354 驱动 C355。
3. 用 `scripts/prepare_client_compatibility.py --dungeon7` 从自己的 `Village_map_image/Village_map_image.pack` 按 `NANA_PACK` 页面／单元结构生成 P03 道路文件；启动器的 `--dungeon7 --apply` 执行同一操作，并保持 `game.exe` 逐字节不变。
4. 创建地宫7的 SSTG 名称兼容文件：将自己的 `flying/hd0_ep22_dg01_st01.sstg` 逐字节复制为 `flying/hd0_ep22_dg00_st01.sstg`；启动器不检查源或产物哈希。
5. 保留资源查找映射 `hd0/ep100/dg6/st1 -> hd0/ep22/dg1/st1`，并从自己的 `flying/pon/mis_ep22_dg01_m_196.pon` 逐字节复制出缺失的 `_02` 同家族回退；启动器不检查产物。
6. 重启适配器并重新登录，使客户端重新读取 C355；从 page17 步行到 page18，再进入 action `166`。验证 SSTG、SMMO、PON 均能按路径加载。
地宫7入口同时依赖**前置进度、村庄道路、关卡资源命名、adapter 资源映射和嵌套 PON**五个边界。

### 3.1 C355 前置进度

第五村使用 C355 完整帧 `+0x80..+0x87` 的独立 64 位前置字段。客户端移动判定对 `k=0..21` 的每个前置要求两个 bit 同时为 1。

完整 adapter 在所有 C355 构造完成后，仅设置低 44 bit：

```text
C355 +0x80..+0x87
FF FF FF FF FF 0F 00 00
```

实现位置：

```text
release/components/dungeon_unlock/unlock_patch.inc
```

约束：

- 只设置 22 个前置对；
- 保留 bit44..63，包括最终完成对；
- 不修改 `+0xC8` 的关卡显示字节；
- 不主动推送 C367/C368；
- 仍由 C354 请求驱动 C355。

### 3.2 P03 村庄道路 pack

原始第五村 pack 只有前六个入口的连通道路，page17 没有通往 page18 的出口。地宫7需要 P03 道路 pack：

```text
Village_map_image/Village_map_image.pack
```

派生器读取 pack 目录与第五村 50×36 单元网格，按字段语义生成道路；不要求原始 pack 或输出 pack 命中固定哈希。

P03 包含 16 条补充双向道路，并保留：

- page17/page18 的原生地宫7入口 action `166`；
- page18 `(25,6)` 的返回 marker `169`；
- 返回坐标 `(400,96)`；
- 已有 `160..166` action；
- 未增加虚构的 `167..182` 地宫入口。

P03 提供道路连通性；战斗资源覆盖范围由 SSTG、SMMO 与 PON 清单独立确认。

### 3.3 地宫7关卡 SSTG 别名

客户端请求的兼容路径为：

```text
flying/hd0_ep22_dg00_st01.sstg
```

使用者应从已有的：

```text
flying/hd0_ep22_dg01_st01.sstg
```

制作**逐字节相同**的别名文件。该复制关系由派生器执行；不对源文件或别名文件设置固定大小／哈希门禁。

只复制 SSTG 文件名；文件内部已经存在的 dg01 SMMO 引用保持不变。

### 3.4 adapter 资源查找映射

地宫7在村庄／房间身份中保留 `hd0/ep100/dg6/st1`，但资源目录使用 `ep22/dg1/st1`。完整 adapter 对**普通目标和 Boss**使用限定映射：

```text
hd0 / ep100 / dg6 / st1
    ->
hd0 / ep22 / dg1 / st1
```

该映射只用于资源查找，不改写房间身份、客户端显示 tuple、奖励归属或持久进度。

### 3.5 PON 同家族兼容别名

关卡嵌套依赖使用以下别名：

```text
源  flying/pon/mis_ep22_dg01_m_196.pon
目标 flying/pon/mis_ep22_dg01_m_196_02.pon
操作 逐字节复制，不设置固定大小／哈希门禁
```

该文件是同家族兼容别名，其外观、轨迹与参数沿用源文件。`gui_launcher/resource_patches/superboss_projectile_alias.json` 记录派生关系和证据边界；GUI 以路径与生成结果为准。

### 3.6 显示边界

客户端 `0x0090012F` 单独控制 d07 小地图图层显示。page17→18 道路、入口 action166 与关卡资源加载使用各自边界；派生器保持该显示站点不变。d07 小地图图层作为独立的原客户端视觉验收项记录。

入口兼容链保持以下边界：

- 新客户端进程的首个 C355 固定发布 `map/page=0/0`，避免原生 `FirstVillageFlag` 在任意存档页面读取缺失入口；
- 首个 C367 不被 adapter 覆盖为存档页面，C367/C368 仍保持请求驱动；
- 家具、入口可见性与碰撞策略保持独立；
- `+0xC8` 表示显示状态，前置进度位于 `+0x80..+0x87`；
- 房间 tuple 保持原身份，资源查找使用限定映射；
- 战斗资源清单只登记实际存在或可重复派生的文件。

### 3.7 验收清单

1. 重新登录，使客户端重新读取 C355 前置字段；
2. 从 page17 正常步行到 page18；
3. 进入 action166，房间选择／创建界面可操作；
4. 进入地宫7，确认 SSTG、SMMO、PON 均按预期路径加载；
5. 三个难度分别验证普通目标、Boss、结算；
6. 死亡、离开、通关后通过 marker169 返回 `(400,96)`；
7. 再次进入地宫7，确认道路、入口和关卡进度保持一致；
8. 记录客户端可见结果、协议元组和关闭方向，分别标注 adapter 构造与原客户端可见验收。
