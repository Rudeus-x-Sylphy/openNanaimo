## 社交模式本机多开：客户端单实例边界与现行多开方案

- 2026-09-29受测客户端为项目根目录的 `game.exe`（长度 `14198272`，SHA-256 `D511D81D172DCE14E108582E0429106170491D18A0781046B24CEDC6B56E2A54`）。
- 该样本通过命名互斥体拒绝第二实例：`0x0043A5A2` 把 `0x00C2C0BC` 的 ASCII `NanaimoClient` 传入 `0x004030B2 -> 0x00AD2F50`；后者执行 `CreateMutexA(NULL, TRUE, name)`，随后 `GetLastError()==0xB7`（`ERROR_ALREADY_EXISTS`）即返回已存在。
- 调用方在 `0x0043A5D9` 显示 `Already Game.exe Run` 并进入启动清理。
- 该摘要标识历史受测样本，不是当前客户端的固定哈希要求。

- 现行多开方案（沿用 2026-09-29 方案）仅用于社交模式：`gui_launcher/start_social_client.ps1` 先验证名称、调用点和 wrapper 字节签名，再把原客户端复制到按“源 SHA-256／社交槽位”隔离的缓存，只把文件偏移 `0x0082AABC` 的13字节名称替换为 `NanaimoSocNNN`。
- 原始客户端不修改；同一槽位重复启动仍受自身互斥体保护，不同槽位可共存；不匹配的客户端版本拒绝启动。
- 2026-09-29 的原客户端验收在已有 PID `18448` 存活时启动槽位902 PID `14028`，10秒后同时存在两个 `game` 进程，随后只结束 PID `14028`（历史验收，不构成当前事实或验收）。
- 现行方案还校验图像共享读取位点，并将副本放在源客户端旁；完整约定见[社交槽位启动](#kb-09-031-1)及[客户端兼容](../客户端兼容/README.md#df-11-002)。

## 社交模式槽位客户端启动契约（准备与注册）

<a id="社交模式槽位客户端启动契约"></a>

- `gui_launcher/start_social_client.ps1` 是社交参与者的多开入口；本地模式继续直接启动未改写的 `$Client`，不得调用该 helper。
- GUI 在后台完成共享兼容性检查后，每个参与者仅调用一次多开入口；入口在同一槽位锁内完成准备和最后运行进程保护，再调用`BeforeLaunch`注册用户名，之后启动客户端并等待可见窗口（默认最多8秒）。准备失败不向适配器排入账号；注册后启动失败仍不能当作客户端接收成功。`PrepareOnly`保留为手工／测试准备入口，不是GUI二次调用路径。返回对象包含进程、窗口、工作目录、运行时目录和副本身份。
- 槽位副本与源客户端相邻，使用 `Game.openNanaimo-social-NNN.exe`；缓存根目录默认为静态资源根下 `.openNanaimo-social`，其内部按源 SHA-256 和槽位编号隔离 `work`、`runtime` 及元数据。
- 准备状态的完整 schema 字符串使用 `openNanaimo.social-client.v5` 与 `openNanaimo.social-worktree.v2`（旧文简称 `social-client.v5`／`social-worktree.v2`）；文件、源根、缓存根、工作目录、配置哈希和图像解析器共享读补丁共同校验。可写配置与 `Working` 独立，静态资源采用目录映射；`APPDATA`、`LOCALAPPDATA`、`TEMP`、`TMP` 指向槽位目录。图像资源探测保留只读权限并允许并发读取，避免同机多开时将共享读取冲突误判为资源缺失。
- **客户端源哈希变化**：当前哈希槽位尚未生成但源目录旁已有副本时，在同一缓存根内查找该槽位的旧 v4/v5 登记。先校验根路径、工作区／配置、目标哈希及补丁范围，再在内存中仅撤销已登记的互斥体／共享读取改动，要求还原哈希精确等于旧源哈希。唯一合法匹配才把旧副本与登记文件保留到旧槽位 `source-update-backup-*`，按当前客户端生成新工作区与副本；旧工作区不删除。输出包含 `SourceRefreshed`、旧源哈希和备份路径。新准备失败回收本次新槽位并恢复旧副本，保留备份供诊断；显式清理旧源副本同样归档，不能递归清空来源目录或账号数据。

## 社交模式槽位客户端启动契约（复用与清理）

<a id="社交模式槽位客户端启动契约-1"></a>

- 槽位复用要求版本、登记身份、内容哈希及唯一匹配全部有效；清理同时校验目录归属与进程状态。验证覆盖源哈希变化、失败回滚、GUI准备与注册顺序，以及P1／P2／P3槽位准备和复用。
- L7/L8 基础凭据保留安装前后链条，不能要求合法修道僧对白覆盖后的村庄包仍等于基础哈希。社交入口遇到源资源差异且存在对白凭据时，调用普通启动同一托管校验器的内嵌配方验证覆盖资格，再逐项比对白、挑战及基础资源在源目录与槽位中的实际哈希；包括根目录复制的资料表。全部通过且源凭据未变化后才同步凭据。未知覆盖、过期副本及链接凭据仍拒绝，不通过改写基础凭据或跳过资源校验恢复启动。实现为 `gui_launcher/lumineos_resource_identity.ps1`，专项为 `scripts/test_lumineos_resource_identity.ps1`。
- 已运行槽位拒绝重复准备、配置改写和清理；槽位互斥串行化准备及清理。进程身份优先按可解析的绝对可执行路径匹配；当 WMI/进程 API 无法返回路径时，只有对应槽位的 `NanaimoSocNNN` 活动互斥体才将同名进程归属为运行槽位，避免失败启动残留的同名进程阻断重试。启动超时或无窗口失败会回收本次子进程；清理逐目标验证缓存边界，对目录联接只删除联接自身。
