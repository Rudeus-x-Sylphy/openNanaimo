### 娱乐室幸运进度与组队结果入口

幸运进度同步在原D008分数处理前更新控制器+168指向的进度对象。积分取完整响应WORD+14并钳位至999，名字保留原对象+28的24字节缓冲区；临时副本明确以NUL结束。更新后恢复寄存器、方向标志及原参数栈，尾跳0x6435D0完成原处理。普通地宫本地结束动画的页面跳转统一交给已完成结果排序的入口，覆盖组队超级BOSS续关中的页面生命周期。

| VA | 接受的原字节 | 目标字节 |
|---|---|---|
| `0x006E31E0` | `CC × 96` | `9C 60 8B 54 24 28 8B 89 A8 00 00 00 85 C9 74 33 83 EC 18 89 E7 8D 71 1C 89 CB B9 06 00 00 00 FC F3 A5 C6 44 24 17 00 89 D9 0F B7 42 0E 3D E8 03 00 00 72 05 B8 E7 03 00 00 54 50 E8 20 2A F7 FF 83 C4 18 61 9D E9 A6 03 F6 FF CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC` |
| `0x0040B37A` | `E9 51 82 23 00` | `E9 61 7E 2D 00` |
| `0x0066CD71` | `74 1A` | `EB 1A` |

应用步骤：

1. 关闭目标客户端和社交槽位，记录game.exe长度及SHA-256，并保存完整原文件。
2. 按PE节表映射以上三个VA，逐站点匹配原字节或目标字节。0x6E31E0为96字节保留代码区，目标剩余部分填充CC；0x40B37A相对JMP进入该代码区，0x66CD71跳往0x66CD8D。
3. 执行下面的结构检查与候选派生，核对三个站点及全部既有地宫兼容项，确认文件长度保持一致、重复派生输出一致。
4. 以`--overwrite --apply`原子应用；工具保存按原SHA-256命名的完整备份，报告中verification.all_pass应为true。社交槽位按更新后的源身份重新派生。
5. 回退时关闭客户端及槽位，按原SHA-256核对完整备份后恢复game.exe；核对长度与摘要，再由恢复后的源身份重新派生槽位。

```powershell
python -B scripts/prepare_client_compatibility.py --source-root "<client-root>" --output-root "<overlay-root>" --dungeon-state --dry-run
python -B scripts/prepare_client_compatibility.py --source-root "<client-root>" --output-root "<overlay-root>" --dungeon-state --overwrite --apply
python -B -m unittest discover -s scripts -p test_social_gameplay_compat.py -v
```

托管启动工具使用同一组构建期冻结的站点配方。专项覆盖原生／目标字节门禁、重复应用、积分0／112／999及越界值、空进度对象、24字节名字保留、原分数处理参数和全部寄存器／标志／栈，以及两种标志状态下结果页数据门控。验证层级为精确迁移和隔离指令执行。

## 娱乐室房内最高纪录

准备房设置控制器支持同一房间的最高分与持有者更新。入口VA `0x00643500` 的原值 `55 8B EC 83 EC 08` 替换为 `E9 FB 00 0A 00 90`，转入VA `0x006E3600` 的256字节区域；区域原值为256个 `CC`，当前值由统一兼容配方生成。处理结束按原调用约定返回，保持栈、非易失寄存器和一次完成。

适用条件：普通44字节完整设置帧沿用原行为；80字节完整扩展帧要求 `frame DWORD+44`=`0x31305245`、DWORD+48等于当前全局资料对象 `+0xD5C` 的房间身份、玩法为1至3、`frame+79` 为NUL。通过后 `frame DWORD+52` 写最高分，`frame+56` 起24字节写持有者，继续更新标题、密码和难度。格式或房间身份不匹配时，仅完成该项处理并保留既有资料。持久结算、榜首比较和成员轮次由适配器维护。

安装步骤：

1. 使用同一发布清单登记的适配器与兼容配方，结束使用待更新客户端副本的进程。
2. 执行 `Nanaimo.Adapter.exe --tools compatibility --source-root <client-root> --output-root <fresh-overlay> --dungeon-state --apply`，在全新目录生成兼容副本。
3. 工具同时校验6字节入口及256字节区域；接受登记的原值或当前值，重复安装保持幂等，其他内容按冲突处理。
4. 核对安装回执、原文件备份摘要及两处当前字节，再由启动器派生客户端副本。
5. 匹配版本的双客户端联合验收覆盖同房破纪录、持有者变化、下一局、普通设置和离房重建；构造与隔离执行结果统一见知识库[工程／验证状态](../验证状态.md)。

恢复步骤：

1. 选取本次安装回执对应的原文件备份，核验大小与SHA-256。
2. 校验当前6字节入口与256字节区域均符合登记配方。
3. 原子恢复入口 `55 8B EC 83 EC 08` 和区域256个 `CC`，保留其余兼容项，并再次逐位点校验。
4. 重新生成客户端副本，通过启动器启动；同一恢复回执保留完整文件身份。

## 娱乐室幸运卡结果显示

本节维护特殊卡代码的结果显示兼容约定。当前娱乐室发奖使用基础卡目录和原生预览；发奖与去重规则见知识库[娱乐奖励](../../业务/娱乐/奖励/卡片宠物与纪录策略.md#kb-07-022-1)，目标分数与计分规则见[娱乐对局](../../业务/娱乐/对局.md#kb-07-022-2)，计分载体见[娱乐对局字段](../../业务/娱乐/对局.md#kb-08-073-4)。

TIME UP后CF86的幸运卡22000011..18由特殊卡目录消费，使用原通用图标和特殊卡记录+245的卡名图片路径，普通／SP／活动卡保持原生查询。名称返回值交给图片加载器，记录+8保存中文文本，+245保存图片路径。特殊卡的大图预览槽归零，三个排名奖励字段及实际入库保留原卡号。

精确配方由`scripts/entertainment_result_compat.py::patch_sites()`生成，归`--dungeon-state`组，并同步内嵌配方：

| 位点 | 原值与当前职责 |
|---|---|
| `0x006E3400` | 192字节原`CC`区，当前存分类／名称／预览包装函数 |
| `0x0064A423` | 原13字节`81 7D 10 80 F0 FA 02 0F 86 AC 00 00 00`；开放幸运卡到`64A430`，其余保留原50000000判断 |
| `0x0064AC90` | 原5字节`E8 E1 04 DD FF`；幸运卡经特殊目录记录+245取卡名图片路径，其余保留`41B176` |
| `0x0064401F` | 原5字节`E8 07 40 DC FF`；幸运卡大图参数为0，其余保留`64B060` |

192字节代码区接受原CC、已登记的旧+8配方或当前+245配方，统一迁移至+245图片路径编码；其他字节按冲突处理。四处位点共保护215字节，实际变化范围由精确配方逐字节核对。专项覆盖八种资源记录、目录分流、图片路径与扩展名解析、预览清理、栈、旧版迁移、幂等和冲突保护，验证层级为隔离x86执行与资源构造。

安装与恢复按[结果页补丁统一流程](竞技结果与复赛.md#结果页补丁统一流程)执行；娱乐室选择框迁移与幸运卡显示兼容项均随`--dungeon-state`应用。恢复时使用该次安装的原文件，或在核对四处当前值后按配方逆序恢复原值；角色与奖励事务继续使用各自持久化约定。
