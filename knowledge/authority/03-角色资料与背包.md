## 200级经验状态与内部版本边界



人物内部权威字段为真实64位累计、等级和CurveVersion3；读取时校验曲线一致性。`NativeDungeonState`采用inventory schema4、payload5704/full5712，联合校验版本、长度和曲线。CurveVersion为3，F10B为v3、payload48/full56。精确布局见`docs/level200/internal-layout.md`；64位累计使用独立尾部字段，宠物经验沿用既有合同。运行产物身份归09。



C355、CF71、C57C、CF88以及任务C59A、竞技/娱乐室结果统一投影为级内DWORD。CF88每条记录按本人状态投影，added是独立真实奖励；不得把级内current覆盖数据库。完整构造清单和迁移流程见`docs/level200/README.md`。200级仍有真实的最后一级经验条，完整区间／停止奖励策略归07；CF71继承lower0、跨级动画/页面缓存/重登仍待原客户端实测；本节不替代09发布状态。

## 统一数据库存储与旧档迁移



正式运行使用`adapter_data/game.db`。已注册角色继续由`Accounts`、`Characters`及按`CharacterId`关联的库存／技能／进度表维护；未注册或克隆角色的草稿、原生工作进程的版本化状态载荷也保存在同一SQLite库的`NativeState(Scope,Name,Content,UpdatedAt)`，不再生成可写DAT或旁路JSON人物档。`Content`为原序列化载荷BLOB，保留已有格式、数值与解析边界，按既有序列化结构存储。`Scope`使用相对数据库目录的命名空间，角色草稿与各原生工作进程隔离；完整项目换目录或仅复制到相同布局的数据库仍能找到草稿。独立原生诊断默认在工作目录使用`game.db`，完整适配器则明确传入主库路径和独立工作进程命名空间。



本文保留的`.dat`、`.handles`、`.new`、`.bak`名称用于迁移识别键与版本化数据库记录名。迁移首次读取旧文件时，在同一事务写入当前记录及`NativeStateImports`原字节副本；原文件保留，但之后读写以数据库记录为准。通过存储接口删除／重置时写`Content=NULL`删除标记，不能因旧文件仍存在而自动复活旧档。旧绝对路径命名空间按实际目录事务迁移为相对命名空间，键冲突拒绝而不猜测覆盖顺序。数据库损坏、读写失败或存储组件缺失不回退到DAT。原生暂存及备份的重命名使用SQL事务；客户端资源与启动INI保持各自的文件存储契约。



原生持久化入口由`release/components/storage/sqlite_state.inc`统一拦截；覆盖账户、商城库存、公寓、宠物配件、等级／称号、技能、卡片、钥匙、引导、合成奖励、快捷栏权限／实例句柄及复活次数。`.handles`也属于持久化账本，不能只检查`.dat`。托管侧`PersistentStateStore`、本地首次注册、启动器离线保存、标题写入和进度重置使用相同数据库契约。启动器等级框用于新角色初始等级，不覆盖已有进度；提示使用1～200级经验表及地宫实时经验／结算奖励，具体奖励规则归07，不再描述固定CF88＋100或等级×100曲线。显式进度重置更新已有角色的Level／Experience、独立HP/MP基线及称号载体（验收归09），不发放虚构五属性，保留任务、技能、解锁及历史排行榜；`DungeonTitleResets`阻止旧标题历史在重登时撤销重置，新的标题奖励仍可正常推进。清理脚本通过数据库删除标记清空原生兼容状态，保留角色、草稿、原档、迁移副本和库存备份，启动配置按收据归档。



## VIP经验卡的主动使用与持久化

翻番卡经主动使用形成有效权益。卡片账本为`CharacterCards`；C3ED的VIP元组由当前在线账户与角色的会话共同授权。一般10、自由20、黄金30分别表示三种钥匙选择。适配器扣费政策为：一般／黄金各扣一把，自由钥匙以合法且有效的到期时间授权；扣卡、扣钥匙及建立`CharacterExperienceCards(CharacterId,CardCode,Expires)`在同一SQLite事务提交。

同一张仍有效卡的重复请求只确认原权益，不二次扣卡或延时。数据库入口默认不允许更换，客户端6201已有结束旧卡、使用新卡的确认流程，协议入口明确允许新卡替换旧权益，但不叠加；失败恢复原权益和库存。数量归零删除卡片行，角色之间独立，数据库重开保留数量和到期状态；原客户端重新登录后的画面验收仍归09。

商城可购买标记保持原目录合同，300%行仍不可购买。随机奖励幸运卡不属于经验权益入口；通用拒绝回0，不能冒充容量不足。C3EE后由客户端自行请求C3E7/50及C3E9，不补发跨控制器库存包。VIP列表分类字节为0，按VIP卡号映射数量及新增提示，不与同为category3的SP／活动卡混槽。

到期字段采用原生按小时编码，适配器把“使用时刻＋目录小时数”向上对齐到可表示整点，覆盖完整目录时长；判定与列表公布采用同一边界。倍率及结算规则归07，协议字段和钥匙链归08，发布及验证范围归09。

## 幸运卡开奖与奖励事务

幸运卡使用独立于type40经验权益的开奖分支，启用A～H八个奖池及`Sddakg._D35`对应的非零奖励记录。适配器将奖品值解释为严格递增到10000的累计区间，均匀抽取0..9999；I/J保留目录占位。验证覆盖八池全部非零奖品的加载与逐项派发。

`OpenLuckyCardAsync`验证账户、角色、在线会话、持卡和神秘钥匙；选奖、扣一张卡、扣一把神秘钥匙、入库及`LuckyCardUseReceipts`凭据共享立即写事务。真正容量不足回100，保存`LuckyCardPendingDraws`但不扣卡／钥匙，腾格或数据库重开后仍发同一奖励；奖池版本或ticket/产物对应关系改变则拒绝并保留待审记录，不重抽。其它拒绝回0，成功900；不能再把不支持的请求直接回100造成6018容量误提示。

奖励SP／翻番卡写`CharacterCards`，每种上限255；普通道具、家具及宠物写`CharacterItems`。容量沿当前投影：普通道具84、家具84、衣物56、购物券256、宠物与材料合计56；真实宠物按代码去重并包括虚拟初始宠物，材料domain17/18/19按数量占格、按材料字段堆叠。真实宠物以目录model/max阶段和0级0经验初始化。**同一只生物按外观归族**（`PetFamilyKey`＝图标去掉单数字阶段后缀＋名字去掉`(n)`等级后缀），目录里的15／30／90／180天及等级变体属于同一只宠物：一个角色每族只保留一行，抽到同族任何变体都写回该行——期限变体按`DurationDays`在剩余期限上**相加**，抽到永久变体则把该行**覆盖为永久**；已获得的阶段／等级／经验、耐久及宝石槽保持不变。判定"是否永久持有"看**该行代码的目录期限**，不看存储值：因此`ItemExpiration=0`的期限宠物旧行只是从未写过期限，下一次发放以该次为起点起算，与限时衣服同口径；而目录期限=0的成品永久宠物（含初始教程宠物）才是真正的永久，再中奖不降级、不发放，按**白抽**结算（整套卡照扣、清除待领记录、固定提示"已拥有该奖励"），页面不再被钉住。到期后该宠物按`ClothingExpirationTime.IsActive`从持有、容量与C44C/C452/C379下发中一并过滤，被抽到时以该次发放重新起算。**商城购买与待领取领取走同一合并口径**：买到或领到同族变体时按上述相加／覆盖写回已持有的那一行，不新增记录；已永久持有同族时该次购买不发放任何内容，按已付款处理且不退款，避免为付费路径引入退款分支。普通道具快捷栏和家具摆放在同一事务按实例序号重排。

同一已授权角色／会话／请求ID的已提交凭据返回原奖励，并发写采用序列化。请求ID使用10秒、最多256项的control＋卡号关联窗口；序号回绕且窗口过期后可建立新请求。幂等范围为该会话关联窗口与持久化提交凭据。验证覆盖回滚、并发、容量及入库，发布范围见09。

## 活动卡独立兑换与显式配置

活动卡兑换只接`C3FD/C3FE`，不复用`C3ED/type20`整页合成。每页十种卡各需至少一张，成功各扣一张；会话授权、单件奖品入库、实例重排和`EventCardUseReceipts`在同一立即写事务完成。容量不足保存`EventCardPendingDraws`且不扣整套卡；更改该页奖池版本不能重抽旧待领奖励，已提交凭据在配置停用后仍可回原结果。请求关联窗口与幸运卡分开，限制相同。同族宠物按上文合并到一行：期限变体相加、永久变体覆盖为永久，抽到已永久持有的成品宠物才走白抽结算并回固定"已拥有该奖励"。

活动卡兑换采用显式奖池配置：从实际数据库目录读取`event-card-rewards.json`，配置有效且页面已启用时进入兑换事务；其余情况返回安全失败并保留卡片。配置为Version1、页1..10、目录内奖品、每次Quantity1、正整数Weight合计10000。产物采用普通商品分支，C3FE的domain13与200各自保留原控制语义。配置说明见`docs/event-card-rewards.md`；自动化验证使用隔离奖池。

`EDdakgi._D19`的页1～4（50000001..40）描述秘密关卡勇士系列，页5（41..50）描述特制套装／钻石，页6（51..60）描述仿福娃宠物／套装／道具，页7～10为占位。现有活动卡开放掉落、拾取与卡册展示，集齐后由客户端启用领取按钮；兑换奖品编号、数量和概率以显式配置为准。响应使用受限固定提示；字符串安全边界、控制条件与刷新归08，配置兑换验证归09。

### C355 副本开放填充与情侣资料边界



For `C354/8 -> C355/728`, access and visible best ratings are separate. The all-open policy normalizes only the 60-byte access table at full-frame `+0x3C..+0x77` to `0x0F` and sets the low 44 predecessor bits in `QWORD +0x80..+0x87` while preserving bit44..63. The score cache is preserved: `+0x88..+0xC3` is the 20-episode x 3-difficulty ordinary table, `+0xC4..+0xC7` is the four-episode secret table, and `+0xC8..+0xDE` is the separate 23-row frontier table. Each score byte packs four two-bit values: 0=no displayed rank, 1=B, 2=A, 3=S.



所有进度写入严格止于完整帧 `+0xDE`。`+0xDF..+0xEF` 是17字节情侣姓名，`WORD+0xF0` 是戒指后缀，`BYTE+0xF2` 是复活次数。无有效情侣关系时，姓名和戒指字段主动清零，使原生姓名门控在戒指资源查找前关闭；只有目录中有效的 `CI._D28/COUPLERING`、代码 `43,000,000+N` 的戒指才可与非空伴侣名一起序列化。不得用伪造姓名、戒指或越界进度填充换取表情翻页。



The final C355 normalizer does not write `+0x88..+0xDE`. Fresh characters therefore retain zero score bytes, while completed ordinary and secret stages restore their persisted best B/A/S rank. Access normalization preserves `+0x78..+0x7F`, bit44..63, couple name, ring, revival count, score bytes, and the remaining tail.



### Ready-room selected-stage rank



CF71 full-frame `BYTE+0xB4` is the selected stage's visible ready-room badge:0=blank,1=B,2=A,3=S; the high byte remains zero. It is derived from the current room tuple and the same persisted ordinary/secret packed best-rank ledger used by C355, but it is not character level and does not modify C355 or CF16. The old managed level write made level1 appear as a default B and is retracted. Static consumption is08; settlement leaderboard persistence is07.



The September25,2026 playable-route audit found a second, independent gap after the first egress correction: retained-native `CF88` settlement visibly carried S (`record +0x0B=5`, score `+0x1C=14478`) and the subsequent CF16 list was emitted, but the native checkpoint commit only persisted clear masks and wrote `DungeonProgress.BestRatings/BestScore` as zero. The next `CF6C/52 -> CF70/12 -> CF71/184` therefore correctly read the still-empty managed ledger and sent blank. The current route now persists the CF88 record only for a non-death `CF87` settlement, binding the member UID and the request-bound `hd/episode/dungeon/stage/logical-difficulty` tuple; it writes ordinary and secret personal best-rank ledgers transactionally, preserves the higher packed B/A/S result, and leaves CF15/CF16 team leaderboard tables separate. Death-inventory/no-progress CF88 is not recorded as a clear. Focused parser, persistence, no-downgrade and route tests pass; September25,2026 user acceptance confirmed the deployed original-client reported scenario.



## 副本等级与称号状态

## 玩家直接交易：C4AF..C4C1



玩家直接交易房间（C4AF..C4C1）与卡片交易所（C5B0..C5B6）使用独立协议。直接交易的格式与方向如下：



- 建房握手为 `C4AF/4 -> C4B0/20`、`C4B1/20 -> C4B1/20`、`C4B3/8 -> C4B4/4`、`C4B5/4 -> C4B7/8 -> C4B6/4`，双方随后各收一个 `C4B9/56` 对端资料。`C4B4` 的 payload 为4字节（WORD结果 + WORD房间号）。

- `C4BA/24` 的 payload 从帧 `+8` 开始：DWORD操作值、WORD对端scene UID、BYTE标志、BYTE交易槽位、四字节卡片元组 `(chapter,page,index,count)`、DWORD卡片代码、QWORD Hans。操作值 `10` 放置／替换卡片，`20` 移除卡片槽，`30` 放置Hans。

- `C4BB/12` 定向确认 `C4BA` 请求方，payload 为 `WORD success + BYTE hansChanged + BYTE slot + card tuple + DWORD code`。对端完整卡片／Hans快照在准备阶段通过 `C4BD/48` 传送。

- `C4BC/0` 保存本方ready并向对端发送 `C4BD/48`（五个8字节卡片槽记录加QWORD Hans）。双方使用 `C4BF/0` 转发确认，最终各收 `C4C0/4`，成功结果为 `10`。



managed adapter 的请求链为 `HandleNativeFrameAsync` 的 `0xC4BA` → `TryApplyTradeOfferAsync`（解析 `+0/+4/+7/+8/+12/+16`，校验目录及库存，更新 `TradeRoom.Offers`）→ `BuildTradeOfferResultPayload` → `BuildNativeFrame`；ready链为 `0xC4BC` → `TryReadyTrade` → 对端 `PendingNativeBroadcast(0xC4BD)`。响应归属分别绑定请求方与对端。



当前验证覆盖操作值、长度、方向、字段布局及适配器字节构造；客户端显示与交互按直接交易场景独立验收。
