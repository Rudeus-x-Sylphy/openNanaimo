# 业务／宠物／成长／寿命消耗与充能

## 范围与适用条件

本页维护宠物寿命的事件消耗、战斗载体、归零及充能。日历期限和独立实例归[所有权](../所有权/家族授予与期限.md)，英雄龙目录上限调整归[资源阶段边界](阶段与奖励策略.md#kb-04-019)。

本页维护CN/KR客户端字段、当前适配器实现和项目策略，适用事件为地宫游戏资料装载与成功复活。偏移均相对完整帧，结果行另行注明。当前验证层级为客户端字段、适配器事务与路由构造，客户端完整游玩验收状态为`runtime_acceptance=false`。

**事件粒度：** 装载一关消耗一次，成功复活再消耗一次。当前适配器将首次有效CFEC作为装载入账点，同地图重发按同一事件处理。CF80维护关卡启动边界，CF88维护结算及清零标志。

## 数值、载体与状态写入

`pi._D7`零基field9是寿命上限，field7是充能单价，field34是日历天数。当前寿命独立保存在逐实例`PetDurability`。目录负值`-1`为无限寿命哨兵，当前值`0`为耗尽，数据库`NULL`按目录初值投影。

CN读写链为`4164AA -> 709230 -> 403418 -> 709260`，写`*(actor+0x7D70)+0xD4`的DWORD；读取为`4180BB -> 709280 -> 7092A0`。KR对应`actor+0x7D78`及相同对象内`+0xD4`。客户端按有符号值直接减1；适配器按有符号语义维护哨兵，并将有限寿命余额钳制至0。

| CN载体／状态元组 | 寿命位置与消费 |
|---|---|
| 背包`C44C`，记录起点`+0x0C`、步长`0x24` | 记录`+0x0E`有符号WORD，当前实例耐久 |
| 充能窗口`CPetCharge`，`C452/2040` | 同上；`8B9240`经`417DFA -> 7CE7C0`写物品展示对象`+0x900`；帧`+2032/+2036`为余额字段 |
| 地宫`CF71/0xB8`，本地／远端成员资料 | DWORD`+0x58`在`6F5282..6F5294`／`6F5837..6F5847`送入同一耐久setter；装备宠物代码位于`+0x38` |
| 地宫`CF72/0x74`，完整应用`WORD+0x64==1` | DWORD`+0x6C`在`6F5C74..6F5C84`写耐久，应用标志1开启覆盖分支 |

## 归零与充能

CN复活界面`73F3A0/73FF50`同时判断支付能力和耐久非0；耐久归零会阻断相应复活操作。结果控制器`763FF0`在耐久为0时调用`40AC5E(actor,0,0)`移除战斗宠物，在特定退出分支遇到耐久为1时通过`41D269(10,0)`清管理器装备槽。KR的`676640/677070/694B40`有对应分支。当前项目策略在耗尽后清理战斗对象及装备槽，保留数据库所有权。

当前充能链为`C451/8 -> C452/2040`，选中实例后`C453/44 -> C454/12`。`8B8BD0 -> 408E31 -> 8B9DA0`构造44字节C453，经`ADA3E0(0,frame)`发送；其`+8`为代码、`+16`为实例handle、`+22`为有符号WORD当前耐久。C454的DWORD`+8=2`经`8B9600`触发客户端重新请求C451，值1为拒绝分支，列表按请求更新。

当前数据库`ChargePetItemAsync`校验在线会话、所有权、确切实例与请求中的旧耐久，在同一事务中扣汉斯并补满：

```text
费用 = (目录寿命上限 - 实例当前寿命) × 目录充能单价
充能后当前寿命 = 目录寿命上限
```

当前适配器的充能资格为寿命上限及单价均为正、当前寿命介于0与上限之间且小于上限；0寿命实例可以补满。KR客户端`7A6DA0`使用相同的差值乘单价公式。零单价宠物的充能资格按当前项目策略处理。

当前990条宠物目录分为577条无日历期限／有限寿命／单价正，49条无日历期限／有限寿命／单价0，356条日历限时／寿命-1／单价0，8条无日历期限／寿命-1／单价0。统计单位为目录条目。英雄龙15003361当前上限50、单价12000；50→49后补满的现行费用为12000汉斯。

## 当前消费策略与事务

当前接入范围是GUI所用托管适配器＋原生桥接地宫链。以下持久化时刻、去重和低寿命处理统一作为项目策略维护。

| 事件 | 当前处理 |
|---|---|
| 首次有效CFEC | 绑定参战`(ItemCode,PetInstanceId)`，同地图代次扣1；寿命50进入后持久化49 |
| 成功金币复活 | 寿命扣1与汉斯支付同一事务；F104/F105确认后发送CF84；已支付待同步请求按同一回执重试 |
| 成功彩蛋复活 | 内部CF95正余次恰减1且HP恢复后，将寿命扣1并入工作进程差量提交事务；CF84 variant60仍只发一次 |
| 死亡剩余1，或剩余2使复活后只剩1 | 转入低寿命失败结算，复活费用保留；结算再扣1并卸下，余额分别为0或1；剩余1的实例保留库存 |
| 进关扣到0 | 原子卸下装备槽；该次寿命事件完成，后续死亡沿耗尽结算处理；CF88对应结果行`+6=1`清战斗宠物显示 |
| 普通胜利／失败、离开或断线 | 保留装载时已提交的消费；低寿命死亡的额外扣减在失败结算处理 |
| 日历期限宠、目录无限寿命或实例负值哨兵 | 保留寿命；期限宠战斗投影统一使用-1，兼容迁移行的既有余额 |

`DatabaseService.PetLifetime.cs`使用立即写事务、活动账号及角色会话校验、确切装备实例校验和`PetLifetimeEvents`回执；主键为`(CharacterId,SessionId,EventId)`。事件键以`NativeBattleEpoch:NativeSettlementCycle`加`load`、成功复活序号或`exhaustion`组成，消费精确绑定实例、会话及工作进程代次，同一事件幂等。寿命钳制至0，耗尽后清装备槽并保留所有权、成长和宝石；`SaveInventoryEquipmentAsync`要求有限寿命实例余额为正，补满后可重新装备。NULL按目录初值投影，消耗资格独立于充能单价。耗尽结算在写事务内重新检查低寿命条件；若充能先提交且余额已大于2，保留充能后的寿命及装备，当前死亡仍按失败结算完成。

充能也使用立即写事务，在读取旧寿命前获取写资格，避免与消费并发时产生SQLite读后写升级冲突；价格公式、请求旧寿命校验和余额门槛保持不变。

`NetworkAdapterService.PetLifetime.cs`在首次有效CFEC提交寿命，按客户端事件顺序投影余额；同地图CFEC按一次有效装载处理。CF71／CF72按来源角色写真实寿命，接收该地图CFEC前的观察者使用事件前余额，已装载者使用事件后余额。彩蛋复活在工作进程回执持久化前，队友CF72使用待提交的事件后余额，与CF84的本地自减保持一致。0寿命卸下后的资料帧使用当前装备槽。

原生动态及旧CF72构造均写实例寿命，CF71的`+0x58`承担同一寿命语义。内部单向`F10C/20`补充寿命元数据，与F100/F102 v4容器分别维护：载荷`+0 DWORD`为工作进程快照actor UID、`+4 DWORD`为工作进程当前宠物代码、`+8 signed DWORD`为寿命。工作进程校验完整长度、当前活动连接UID及宠物代码后，将寿命写入连接槽元数据并绑定`join_order`代次；HP/MP、背包及成长沿各自同步通道维护。F10C限内部桥接使用，客户端外部入口拦截F100..F10C。托管接收回调使用桥接写锁直接发送。库存充能／换装导入后重新同步寿命；0寿命卸下后，下一次CF70前先导入当前装备槽，使续关使用当前宠物及宝石加成。

实现入口为`managed/Services/DatabaseService.PetLifetime.cs`、`DatabaseService.NativeDungeon.cs`、`NetworkAdapterService.PetLifetime.cs`、`NetworkAdapterService.NativeDungeon.cs`、`NetworkAdapterService.NativeDungeonRevival.cs`、`release/components/game_session/managed_bridge.inc`及`release/components/protocol/protocol_state_sync_base.inc`。`scripts/test_pet_lifetime.py`验证资源迁移，`tests/PetLifetimeRegression`验证消费事务及路由。

## 验证归属

竞技／娱乐室寿命、不同地宫阶段与连续挑战的入账粒度、零单价宠物充能资格、耗尽后库存和异常中断入账时刻按各自模式及事务归属维护；本页给出的持久化、保留库存及低寿命失败结算规则适用于当前项目策略。

当前验证层级为客户端字段、适配器消费事务、路由及原生生命周期。客户端完整游玩验收状态为`runtime_acceptance=false`，具体覆盖归[宠物寿命验证](../../../工程/验证状态/文档与静态调查记录.md#宠物寿命静态调查)。
