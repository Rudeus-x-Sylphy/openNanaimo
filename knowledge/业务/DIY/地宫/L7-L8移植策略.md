# DIY／地宫／L7／L8移植策略

本页提取L7／L8代码和资源移植中的通用接入约束。现行资源包包含L7整关战斗闭包替换与L8新增战斗资源；文件名、通信身份和资源内部身份必须分别核对。

## 身份映射与选槽

| 对象 | 通信元组 | 资源查询元组 | 转换规则 |
|---|---|---|---|
| L7第一阶段 | `0/100/6/0` | `0/22/0/0` | `episode=16+dungeon`后资源dungeon归0。 |
| L7第二阶段 | `0/100/6/1` | `0/22/1/1` | 明确保留L7 BOSS的dg1例外；兼容SSTG别名不会改写内部SMMO引用。 |
| L8第一阶段 | `0/100/7/0` | `0/23/0/0` | 韩服SSTG内部`0/1/0/0`转换为通信元组。 |
| L8第二阶段 | `0/100/7/1` | `0/23/0/1` | 韩服SSTG内部`0/1/1/0`转换为通信元组；保留实际引用的`dg01_st00`槽文件名。 |

`DungeonCombatCatalog.ResourceIdentity`仅在`hd0/ep100/dg0..7`执行资源查询别名；原生侧也须保持相同边界。房间字段、奖励归属、持久进度和导航仍按通信身份处理。

L8生成器逐阶段读取九个实际SMMO槽，各槽分别生成目录。PON传入攻击查询使用`difficulty*3+真实stage`的选择规则；该查询规则不能当作把九份候选SMMO拼成一份运行目标列表的理由。

## 整关替换与共享依赖

| 步骤 | 检查与目的 |
|---|---|
| 基线审查 | 先比对CN／KR字段模型。L7 BOSS样本韩服91行、CN29行，不能只换一个BOSS文件而保留不匹配的MMO／PON／EFF。 |
| 显式转换 | `port_lumineos_resources.py::build`分派`mmo200`、`pon106`、`sstg-l7`、`sstg-l8`、`village-pages`等配方；源、CN基线和输出各有摘要校验。 |
| 共享资源 | `retain-cn`保留已确认共享定义，`preserve_l7_combat`只约束清单登记的保留项。它不表示现行包完全保留旧L7战斗版本。 |
| 兼容别名 | L7的`hd0_ep22_dg00_st01.sstg`与源`hd0_ep22_dg01_st01.sstg`按登记关系复制；PON同家族别名亦按当前资源身份生成。 |
| 场景与道路 | 合并第五村地图并识别原生L7／L8布局；道路派生须幂等，不能把CN旧格点坐标直接套到韩服原生布局。 |
| 数据再生成 | L8普通目标、BOSS、PON攻击、碰撞／地形、掉落、最大分及托管目录一起发布；L7保留项逐条复核。 |

## 导航、成绩与验收

| 业务 | 接入约束 |
|---|---|
| 阶段推进 | 允许本区域两阶段及同阶段重试；L7→L8合法，L8→L9不合法；必须验证CF8B请求与CF8C响应。 |
| 难度 | 保留hd／episode上下文，L8不套普通村庄dungeon2的难度改写。 |
| 成绩 | 按独立区域、阶段、难度持久化；资源别名不改变成绩归属。 |
| R8 | grade24、文本2397、图标1267；成功stage1授予，失败不授予；旧grade23迁移遵循既有规则。 |
| 验收 | 转换、原生结构解析、托管构造及事务验证分别登记；这些检查不替代原客户端画面、BOSS行为和完整游玩。 |
