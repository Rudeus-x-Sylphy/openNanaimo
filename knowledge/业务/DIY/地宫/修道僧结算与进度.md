# DIY／地宫／修道僧结算与进度

定义重试／回城、本人结果对白、独立通关位、幂等结算收据及四关独立排名。

## 加载、重试与结算

准备房进入现行加载确认与开战周期，结算冻结当前角色结果。结果动作限定为同关同难度重试和回城；重试建立新的战斗周期并重新等待加载确认。

精确`hd0/ep24..27/dg0/st0`的结果输入点`0x762F74`接原重试路径`0x763C69`，绘制点`0x76523A`接`0x7653A7`。其他元组分别接回`0x762F7B/0x765240`。manager `+6`、controller `+4`、结果状态和窗口占用门共同约束动作资格。

| 控件／动作 | 对象字节偏移／消费点 | 挑战规则 |
|---|---|---|
| retry | `+0x58`，构造点`0x75CAF6` | 挑战分支轮询并绘制；按键`0x40`触发重试。 |
| exit | `+0x5C`，构造点`0x75CC70` | 挑战分支轮询并绘制，返回来源村庄。 |
| continue | `+0x60` | 本例结果页使用retry／exit。 |
| boss | `+0x64` | 本例结果页使用retry／exit。 |
| nextdg | `+0x68` | 文案随所属难度规则变化；本例不开放下一地宫动作。 |
| 挑战重试协议 | `0x4032DD → 0x6EA920` | 构造`CF8B/12、WORD+10=1`，维持同关同难度。 |
| 普通地宫后续协议 | 按键`0x3F`、`0x4183F9 → 0x6EA970` | 使用mode2分支，资格归所属普通地宫规则。 |

### 胜利与失败后续对白

结果反馈采用“开战冻结身份 → 接收本人评价 → 回原村庄授权 → 显示一次”的状态模型。

| 状态转换 | 消费点 | 检查／效果 |
|---|---|---|
| 开战冻结 | `0x6F749D` | 建立挑战代次，冻结episode、本人UID和来源村庄／页面；重置上轮待显示结果。 |
| 本人结算 | `0x6FA2CF` | 匹配本次episode与本人UID；临时row的BYTE+0xA4评价0失败、1～5通关，保存待显示结果。 |
| 返城授权 | `0x53CE10` | 恢复原来源位置，消费结算资格并授予一次显示资格。 |
| 村庄就绪 | `0x52A751`在`0x527C80`之后 | 检查来源、MyInfo UID、本地角色`+0x3B0` UID、光标`+0x334`及窗口管理器。 |
| 创建／消费 | 角色与光标就绪、窗口空闲、分配成功 | 创建带本村立绘的四行对白；成功建窗才消费显示资格。 |
| 来源失效 | 来源变化或角色切换 | 清除授权，避免显示队友／旧角色／旧周期的结果。 |
| 绘制／关闭 | 原结算更新点`0x762F09`使用`8B55EC837A3C01`；村庄最终UI绘制 | 结果对白末页或Escape关闭。 |

| challengeIndex／episode | 成功文本ID | 失败文本ID |
|---|---:|---:|
| 0／24 | 6001 | 6002 |
| 1／25 | 6004 | 6005 |
| 2／26 | 6007 | 6008 |
| 3／27 | 6010 | 6011 |

该状态模型保证本人当前挑战的结果与返城场景一致。

## 独立进度与状态记录

| 记录 | 主键／字段 | 规则 |
|---|---|---|
| `CharacterMonkChallenges` | 主键CharacterId；`ClearMask`、`UpdatedAt` | 四关各占一位，范围0～15；旧角色首次读取返回0，重新登录恢复已有掩码；accountId与characterId联合校验角色归属。 |
| `MonkChallengeCommits` | CharacterId、SessionId、SettlementId、BattleEpoch、SettlementCycle、ChallengeIndex、Rating、CommittedAt | 角色／会话／结算ID唯一；SettlementId规范`epoch:cycle`，epoch>0、cycle>=0，成功评价1～5。 |

结算提交顺序：

1. 结算服务校验单人资格、精确挑战身份、当前周期及冻结本人结果；数据库另核验角色／账号会话所有权。
2. 同一事务写成功收据、`ClearMask | (1 << index)`及独立最佳分／评级，外层事务提交后才持久化；重复成功返回幂等结果并保留已提交的分数与评级。
3. 按战斗代次和结算轮次拒绝陈旧提交；离线恢复要求角色和账号的所属会话均为空，并沿用已认证结算身份。
4. 主线、称号、全地宫开放、货币、经验与库存分别维护所属状态；显式启用的[跨村授权](../../角色/新手引导/跨村前置.md#修道僧跨村授权)读取既有通关掩码。新成功结算同时尝试写入[当前章节任务凭据](../../角色/任务/章节剧情移植进展.md#修道僧目标与任务槽)；仅对应任务步骤已激活时有效，旧通关位、早于任务的挑战和离线日志恢复不补造章节完成。

## 四关排名与成绩展示

- `MonkChallengePerformance`以`CharacterId/ChallengeIndex`为主键，四关对应`hd0/ep24..27/dg0/st0`，每关单槽保存`BestRating/BestScore/BestElapsedMinutes/ClearedAt/UpdatedAt`；兼容列`Difficulty`由数据库CHECK固定0。入口、重试、结算及查询不接受非零挑战难度。成功结果在已认证单人结算事务内提交；重复、陈旧、越权和失败提交保持原成绩，较低重试保留最佳值。可靠耗时缺省为NULL，通关位与历史成绩独立保存。
- 已存在旧三列主键的数据库在可写启动或成功结算事务中迁移；按角色／挑战分别取最大评级、最高分和最早ClearedAt。最高分并列时优先已知且较短耗时，再按UpdatedAt、旧Difficulty稳定选行；耗时与UpdatedAt取获选分数行，不能挪用另一分数的耗时。新更高分无可靠耗时则恢复NULL。建新表、复制、删除旧表和重命名均在同一事务；失败回滚，重复初始化不重复迁移。只读查询不造表、不凭旧通关位或重复收据伪造成绩，正式升级须先完成可写初始化。
- CF15→CF16按当前授权挑战单槽查询，显示选择器限定0，合法元组限定hd0、ep24～27、dg0、stage0、difficulty0。非零难度的数据库查询返回空榜，协议路由拒绝该请求，不别名到其他玩法。十行252字节完整响应使用既有姓名、真实人物等级、精确称号布局和通用排序。托管与保留原生出口统一采用真实成绩并按请求返回榜单。
- 准备房CF71的`BYTE+0xB4`投影本关单槽最佳评价：D/C为空白徽标，B/A/S为1/2/3，`+0xB5=0`；非零难度不读成绩。普通、秘密、第五村评级、主线与称号各自独立维护。
- popup51显示四行，每行Epi框内使用原生数字贴图`01/02/03/04`，只有一个评级格，不显示难度表头或多阶段列。提示文案左侧填写当前挑战关卡名，来源为`manifest/monk_localization.json`的2504～2507。C355完整帧`+0xC8..0xDE`仍为23字节缓存：row0～7归第五村，row8～11分别是一个挑战的0～3评级字节，row12～22为0。挑战不应用普通地宫的客户端难度0/1/2到逻辑索引1/2/0映射；重新登录从真实成绩恢复，全开放只控制进入资格。
- `IS_CHALLENGE`限定扩展适用元组：`0x8C25A8`接popup初始化，`0x8C30ED`接数字及标题绘制，保留原窗口、关闭按钮与48槽更新／释放，只有前四槽创建徽章。数字复用`0x8C2806`的`0x41CC33 → 0x41E0E7 → 0x40A62D`链与`0xCA5AE4`资源字符串`images\interface\000008-nanaimo_pop_mybag_num.im3`，由`0x402770`选择帧；八个数字指针写入窗口`+0xEC..+0x108`，由原析构`sub_8C2170`释放。标题复制到窗口`+0x110`，使用原`0x41206C → 0x40DA1C`文本ABI。`0x6FA50D/0x6FA591`将CF88评级getter／setter导向row8～11，以单槽最大值更新；getter／setter另校验调用参数hd、episode、difficulty0及stage0，参数不匹配或其他元组回原路径。
- 原窗口链由`sub_8C2580`初始化、`sub_8C3050`绘制、`sub_8C2330`构造评级图标；`sub_544000 -> 0x416B30 -> sub_4D0FB0`恢复23字节表，`sub_4D1370`读取两位评级。兼容配方由`scripts/monk_dialogue_compat.py`和`managed-host/Resources/client-compatibility.json`共同维护，按已登记精确字节迁移，并验证代码区和全部入口。
- 原普通背景`interface/nanaimo_cs_pop.eff`引用的`nanaimo_cs_pop01.im3`含烘焙的难度／阶段矩阵。`scripts/monk_ranking_resources.py`核验原资源SHA-256后派生挑战专用`openNanaimo_monk_rank.eff/im3`，尺寸由554×336收窄为450×336；按纵向分段移除闲置横向像素，保留原边框、完整提示／页脚、Epi框和关闭图案，不缩放字体。数字坐标为`(253+14*(i%2),273+38*(i/2))`，评级坐标为`(431,268+38*row)`；标题锚点为`(357,181)`。下方关闭与右上关闭控件分别移到`(557,428)/(599,141)`，通过`0x410DFC`移动图像并重算控件`+8`命中矩形；EFF阴影横向比例为450/554。普通、秘密和第五村原资源不覆盖。两项资源由`prepare_monk_dialogue.py`加入同一安装／恢复事务，必须与新代码配方一起生成及部署。
- 专用背景的表体清理覆盖原图`y=84..283`（含末行），`y=99..277`清理到`x=530`；底部六行按原右下圆角边界收口，保留顶部铆钉、真正外框与`y>=284`页脚。每行单槽取原矩阵内侧圆槽`x=148..180`，避免复制最左槽时夹带第四行的外框圆角。收窄后的`x=416..426`不保留旧表头或半槽，末行不得残留旧三组矩阵的底边。像素回归须检查清理区和外框保留区，不能把包含旧列的整个右侧区域当作必须原样保留的边框。
- 四关单槽为项目接入策略，客户端显示与角色成绩按同一挑战编号对应。
- 既有验证范围为适配器路由、SQLite事务、x86兼容逻辑和资源构造；发布身份由活动清单登记。客户端完整挑战及排行榜已获用户验收确认，范围与受测版本待补录状态见[修道僧挑战验收](../../../工程/验证状态/修道僧挑战验收.md#四关排名验证)；原清单`runtime_acceptance=false`不自动改写。程序位点、资源与安装恢复归[四村对白安装](../../../指南/客户端二进制补丁/修道僧四村对白安装/索引.md)。
