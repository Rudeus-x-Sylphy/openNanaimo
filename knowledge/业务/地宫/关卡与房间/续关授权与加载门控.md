## 结算页等待与动作授权

- 结算的两个控制器分别具有本地timer，action-state5属于鼠标确认路径。
- `--dungeon-state` 关闭两处自动倒计时并恢复鼠标确认；普通关卡继续、第三关超级BOSS挑战与最终页重试由玩家输入驱动。
- CF88完成原生结果排序后，普通地宫战斗控制器进入已初始化的评分页；观战成员同步使用该入口。
- 进入评分页时将键盘及鼠标的上一帧快照更新为当前输入，确认使用评分页上的新输入变化。
- 适配器按`SettlementAwaitingAction`、合法的存活或失败重试状态、完整12字节CF8B及mode1/2校验推进条件；失败只允许mode1同关重试。
- CF8B携带动作模式，输入来源由客户端控制器处理。

- 连续挑战保留房间与角色资源，切换到下一地宫时同步所有活动成员的完整准备房状态，并建立新的房间加载周期。
- 原生工作进程为队员同步关卡选择和连接局部加载阶段，随后分别完成资料、同伴连接及最终开始确认；续关状态以成员代次隔离，阶段流程见[房间、加载和多人同步](房间身份.md#kb-05-000)。
- 新战斗开始后生命、法力和火力继续按战斗规则更新；准备房与结算界面的主动回城保持独立。
- 超级BOSS成绩按实际关卡阶段持久化，显示阶段独立处理。

## 跨难度续关

| 来源 | 目标 | 条件 |
|---|---|---|
| 普通地宫 `CF8B/12 mode2` | 普通阶段进入同难度下一副本 | — |
| `dg2/st1` 超级BOSS成功结算 | 以 `real0` 进入下一客户端难度的 `dg0/st0` | 目标资源存在、源阶段合法且客户端难度小于2 |
| 失败结算 | `mode1` 同关重试 | — |
| 拉米诺斯（Lumineos） `hd0/ep100` | 独立下一副本策略 | — |
| 修道僧结果动作 | 限同关重试与回城 | — |

- 客户端application难度`a`按0→1→2递增。
- `CF6C WORD+0x26`由getter写出，`CF8C WORD+0x2C`写回同一字段。
- `NativeDungeonLogicalDifficulty`及持久成绩索引使用轮换编码`p=(a+1)%3`，沿1→2→0映射；源索引0对应客户端最高值2。
- 升难度响应为`CF8C/48 real0/show0/dungeon0`、`WORD+0x2C=a+1`。
- 存档格式和成绩投影沿用该映射。
- 原生`managed_record_clear`在结算写通关位时将资源选择器转换为p；`progression_current_dungeon_tuple`在输出普通／秘密超级BOSS的旧frontier字段时使用既有编码，战斗上下文保持资源difficulty。第五村保留独立身份与记录边界。

- `TryResolveNativeDungeonTransition`验证目标副本、阶段及客户端编码后更新索引、保留续关授权并初始化重载；资格校验失败时保留结算动作。
- 结果页`0x7600C6..0x760448`按application值与章节选用按钮：值0使用`middledg`；值1在`hd0/ep2或3`使用`middledg`，其他分支使用`topdg`。
- 例：`hd0/ep2/dg2/st1/a1/p2`成功后，升难度目标为同章节`dg0/st0/a2/p0`。

- `dg2/st0 → dg2/st1`的mode1挑战保持资源／客户端选择器a和持久索引p各自原值；p用于存档、成绩投影和托管授权，SMMO按a选槽。同阶段成功或失败重试保持已确定的资源身份。
- 连接difficulty、地图difficulty、CF8C的客户端难度和CFEC的资源槽位属于同一资源选择器a；绝对槽位为`a*3+real_stage`，超级BOSS阶段a=0／1／2分别使用槽位1／4／7。
- 难度变化提示仅随成功结算后的mode2升难度触发。

- 原生过渡先识别超级BOSS mode2，源资源选择器a=0或1时验证`a+1`的目标资源并升到该难度的副本0／阶段0；a=2保持最高档边界。随后更新地图与成员元组、重置加载屏障，并完成`C587/CF70 → CFEB/CFEC → CFD3/CFD5 → CF7F/CF80`加载链。托管授权按既定映射更新持久索引，存档沿用现有格式。
- CF99拥有所属入房初始化分支，普通续关采用既有房间状态。
- 房主先提交新元组时，`IsNativePartyContinuationSourceSelectionCurrent`使用带目标客户端难度的临时响应校验队员资格。
- 资源冻结、死亡返回和成员代次沿本页现行规则处理。

资源选择：普通第2～16章的超级BOSS资源名按a=0／1／2选择`_L_01.smmo`／`_M_01.smmo`／`_H_01.smmo`。第12章（ep11）三模式的每模式HP分别为49,680／66,240／115,920，三模式累计149,040／198,720／347,760。普通阶段和第五村`hd0/ep100`使用各自资源选择器。资源及宿主构造的验证归[地宫跨难度续关验证](../../../工程/验证状态/地宫与成长验收.md#地宫跨难度续关验证)。

| 边界 | 地址/调用链 | 验证用途 |
|---|---|---|
| CF8B/12 构造与提交 | `0x708760`构造CF8B及完整长度12；mode2发送器`0x6EA970`在`0x6EA981`写WORD+0x0A，经`0x6EA99A → 0x40A821 → 0x6E90C0`提交；结果输入`0x762A30`经`0x4183F9`调用该接口 | 续关动作模式的提交边界 |
| CF8C 消费 | `0x6FBD28..0x6FBF61`读取BYTE+0x28/+0x29、WORD+0x2C/+0x2E；`0x6FBEDE → 0x4170D5 → 0x50A260`写全局difficulty `+0x1E528` | 资源episode小于16时写副本选择 |
| 难度提示门与结果控制器清理 | `0x6FBE94..0x6FBECC`比较旧application难度与CF8C WORD+0x2C，经`0x401D8E → 0x708EE0`写BYTE+0x1FAF6；加载页`0x70DC10`经`0x40D4D6`读取并触发提示；`0x6FBF5C`执行配套结果控制器清理 | 提示随成功结算后的升难度路径触发 |

结算页食物和换宠保留续关授权，库存响应规则归[结算页食物与队列边界](../../库存/消耗品/食物与通用使用.md#结算页食物与队列边界)。验证归属见[地宫与成长验收](../../../工程/验证状态/地宫与成长验收.md#结算库存与挑战入口验证)。

## 结算续关标志与加载分支

- CF99离场标志（REQ_FLYSHOOTING_SURRENDER_ABUSER）构造 `sub_7089F0`、发送 `sub_6EAE60`，指令 `0xCF99`、长度8；发送调用0x66C190/0x66C6C9后写manager+7。
- 控制器在计数器超过 `0xE10` 时于 `0x66C190/0x66C6C9` 发送CF99（计数单位未确认），随后 `0x66C19E/0x66C6D7` 设置应用字节+7；应用对象+7的setter为 `sub_66E5E0`、读取为 `sub_66E600`。
- CF9A不清除该标志；CF6D状态10达到的清除辅助函数归本条下方登记的CF6D清理链。
- setter thunk0x40D24C的已恢复xref为0x66C19E、0x66C6D7和0x70850D：前两者分别紧跟CF99发送并写1，后者由CF6D清0；这支持按实际收到的CF99登记连接门控，不以单纯阵亡代替该写入。
- CF8C从0x6FBE40读取该字节：非零在0x6FBE53..0x6FBE61进入结果控制器3，零从0x6FBE66走正常重新加载7。CF99调试名本身不能证明计数单位或处罚机制。
- CF6D status10 的调用链与写入对象：

| 调用链 | 写入对象／用途 |
|---|---|
| 0x6F7973 → 0x4067AD → 0x7084F0 | 设置application+6 |
| 0x41781E → 0x708530 | 清DWORD+8 |
| 0x40D24C → 0x66E5E0 | 清BYTE+7 |
| 0x6F7992 → 0x405AE2 → 0x6E9440 | 发送CFD1并改网络控制器+0x7C |
| 0x6F7B67..0x6F7B70 经 0x403B70/0x72EFE0 → 0x416793/0x7366D0 | 进入状态8 |

- 结论：CF6D status10 不是无副作用的清标志包。

- 44字节原生帧覆盖其直接消费的+8/+9/+0xA与+0xC..+0xE。
- CF78 status10在0x6F7EDA切换独立控制器8，清理发生在CF8C之后，不能修正已选中的离场分支；不能据此反推无CF99的正常续关也应补CF6D。

- CFD2回复在0x6F493A..0x6F4941调用0x417B02 → 0x6E94C0发送C587/CF70；CF8C的0x6FBF53..0x6FBF5C独立令结果控制器进入重载7，普通结果循环0x763FF0在0x7646E8..0x764738检查state7与+0x18门，再由0x764707调用同一发送器，随后进入state6。

- 另一结果循环对应调用点0x770100。
- 发送器的application+6门、12字节CF70构造0x708400/0x404165、+8取network-controller+0x7C及0x6E951B发送链保留；因此额外CF6D可以引入两轮真实资料请求，而不是仅客户端调试文本的重复打印。

- CF71本地UID匹配后的无条件 X=-300 与两种Y常量（`0x6F504B..0x6F506D` 写入窗口）归[房间角色、加载、地图和继续条件门控](加载与开战.md#kb-08-023-1)的“本地位置 CF71”行；该行 `BYTE+0x56` 即本页 `slot`，两种Y值公式按该行原样登记。
- 它不检查本地actor是否已经在移动，远程分支的已有对象门不能用于本人。
- CFDA已登记的入场目标为Y=151+100×slot，故slot0的迟到CF71可以覆盖正在去往151的本人坐标为252。
- 续关状态边界归[房间、加载和多人同步](房间身份.md#kb-05-000)，十个关键代码区通过当前客户端字节校验。

- CF8C完整48字节覆盖实际／显示BYTE+0x28/+0x29、难度WORD+0x2C、副本WORD+0x2E。
- +0x2C经0x6FBE94..0x6FBEE3与application当前难度比较，并通过0x4170D5 → 0x50A260写DWORD+0x1E528（getter 0x411ACC → 0x708550）；它不是房主UID。
- 资源 episode 小于16时读取+0x2E的既有条件不变。
- CF8B分支已将错误的“room-owner UID at +0x2C”注释纠正为difficulty WORD；构造器按difficulty写该WORD，不能把数值0误读为房主丢失。

- CF6D在0x6F795D读取BYTE+8成功状态；0x6F799D独立读取BYTE+9，经0x6F79AE／0x6F79BE → 0x409BC4 → 0x708C00写application BYTE+4房主标志。
- 下一次CF80的0x6F762B..0x6F766C通过0x402BDA → 0x708C20读取+4，再通过0x408D19 → 0x708C40读取+5：两者均非零时保留续关路径，其余组合进入准备房控制器state3。
- 44字节成功响应以两个独立BYTE分别表达状态和房主身份，房主标志按当前角色保留。
- 适用范围为角色身份和开战分支。

- 连续关卡资源恢复使用已授权CF8B/12与捕获CF8C/48的real/show BYTE+0x28/+0x29。
- 随后CFEB/12的WORD+8/+0xA必须逐项匹配；捕获CFEC必须完整808字节，BYTE+0x2DA/+0x2DB匹配同一real/show。
- NetworkAdapterService.DungeonContinuation在响应原顺序中完成解冻：CFEC前D010仍按结算冻结丢弃，之后D010/36由本地UID和WORD+0x10更新资源再转发；BattleResourceSnapshot.ForEpoch保留HP/MP/P，只重置冻结及HP优先级。
- 此为适配器源码／构造边界，不新增客户端反汇编结论；原客户端下一关可见扣血待验收。

## 续关授权与成员代次

- 多人地宫续关按房间代次、战斗周期和成员会话分别登记；房间完成有效下一阶段授权后，成员沿同一已确认阶段恢复，使用房间已确认的阶段身份。成员离场会清理其房间成员、战斗参与和准备态残留。
