## 第七关拉米诺斯（Lumineos）副本：超级BOSS资源与重置边界

**第七入口超级BOSS阶段路径。** 普通BOSS结算后，CF8B mode1 与 CF8C 进入 stage1。客户端资源路径为 `hd0_ep22_dg00_st01.sstg`，关卡内部资源使用 ep22/dg1/st1；适配器通过限定映射和 SSTG 名称别名连接两套身份。

当前资源事务的 `hd0_ep22_dg01_st01.sstg` 与 `hd0_ep22_dg00_st01.sstg` 兼容别名均为98,444字节，SHA-256均为 `0F50B551670DD401480E56E9DDFA6D9CD9220193CE942EB8E9A89709051612A4`，见 `manifest/l7_combat.json` 的 `inputs`。

以下为整关韩服替换前的CN资源检查样本，保留其字节数和验证统计用于历史追溯，不作为当前安装文件的大小、目标数或验收结论：

- 当时对应资源为 `hd0_ep22_dg01_st01.sstg`（103124 字节）。
- 其三层名称、九个嵌入的 dg01 SMMO 名称和所有 89 个直接提取的资源名称均有对应文件；这些层引用了 21 个现存的 IM3 名称。
- SSTG 和九个 SMMO 在两个分发样本中一致（20次精确比较）。
- 当时CN目录的 ep22/dg1/st1 普通配置文件分别有 893/927/921 个目标，这些目标在三个难度级别上重复出现；九个BOSS配置文件各有两种模式。
- 旧CN资源目录记录的模式总HP为280000/337463；这是替换韩服L7战斗目录前的历史数据，不是当前生命值，也不构成可见血条验收。
- 当前L7两模式合计4,289,329的口径见[BOSS生命比较](../BOSS/生命来源与比较.md#kb-06-004)。
- 不要将九个 SMMO 连接起来或更改普通/BOSS/奖励算术。

ep>=16 的 CF8C 分支使用显式副本设置器；父级普通查找与BOSS查找把 wire `ep100/dg6` 映射到资源 `ep22/dg1`。stage1 的九个查询均按该限定映射解析。

- 兼容性策略使用与源SSTG字节一致的 **SSTG-only** dg00_st01别名，保留内嵌dg01 SMMO名；普通目标／BOSS查找只将hd0/ep100/dg6/st1映射到ep22/dg1/st1，不改变房间身份、槽位、道路、战斗／奖励算术或角色资料，也不能据此推断原始命名意图。
- 适配器验证覆盖三个难度下的普通BOSS -> 请求驱动stage1重新加载 -> 两种BOSS模式 -> 单次最终CF88，以及中间／重复奖励抑制和周期／请求门控。
- 独立构造检查包含106个请求驱动重置响应（序列／低位／长度／模式／静默门控）、55个隔离x86分支、9个stage1查找缺失和1692个直接查找。
- 每个查找家族的9个别名保留1692个直接查找与117个既有别名，并检查4896个hd/episode/dungeon/stage边界元组。
- 以上均不证明客户端资源加载、多模式战斗、子对象回收、掉落、CF87/CF88渲染或村庄返回／重新进入通过。

## 超级BOSS重置和命名资源加载

- 请求构造器0x708760 写入CF8B/12；模式1发送器0x6EA920 写入实际/显示BYTE+8/+9和模式WORD+0xA=1，并通过0x40A821发送。响应分派器0x6EBAC0 的case53132是0x6FBD28..0x6FBF61。现有的应用程序+7/CF99门控条件保持有效；提供的失败遵循正常的重新加载分支。
- 正常分支CF8C的0x6FBE66..0x6FBF5C部分通过0x4013A7 ->0x708D40（manager+0x1E540）分别写入实际阶段、难度和关卡。
- 在0x6FBEEA处，0x418499 ->0x6772B0读取资源episode+0x1E534；在0x6FBEEF处进行比较，16与0x6FBEF2处跳转至0x6FBF22，当资源episode（ep）>=16时执行。
- 只有资源episode（ep）<16时，在0x6FBEFA/+0x6FBF11处读取WORD+0x2E，并调用0x408CAB ->0x708D20（resource dungeon+0x1E538）和0x41B8B0 ->0x708DA0（wire dungeon+0x1E54C）。
- 因此，资源episode（ep）22的重置忽略了响应中的副本（dungeon）字段。
- 上述分支共用的 CF8C 字段布局（最小完整长度48字节、BYTE+0x28/+0x29、WORD+0x2C/+0x2E）归[CF8C消费](续关授权与加载门控.md#kb-08-066)。
- A55-case隔离的本地-x86执行仅使用一个单例419BBE钩子，并执行实际获取/比较/设置操作；它保留了字段0/1/6/255/65535和资源episode（ep）0/15/16..23/100的边界。
- 这不是完整的客户端运行。

- 0x66EC30 将资源获取器格式化为 `hd%d_ep%02d_dg%02d_st%02d.sstg`；0x41F2D5 ->0x69BAD0 在 `flying/` 下打开，测试流的 `is_open` 通过 0x40763F ->0x43E0E0 ->0x40752C ->0x4414B0 (filebuf+0x4C 非零)，并在成功分支内进行解析。
- 文件打开 0x4162A2 ->0x43E100 将零结果传播到流失败状态；CF8B 发送 0x40A821 ->0x6E90C0 ->0xADA3E0 使用连接对象+0x78。
- `CShootingStage::Open ... Closed` 底部即使打开失败也会执行。
- SSTG 字节通过 XOR0x28 进行处理；它通过 0x40FBFA ->0x6A0620 向阶段对象+0x21C+260*槽提供九个260字节的 SMMO 名称。
- 0x69D510 读取选定的名称，而不是重新生成的 dg00 文件名。
- 旧CN ep22 样本第一个名称位于文件0x5AA0，下一个八个位于步幅0x20C；该文件偏移属于该样本，不能直接套用当前韩服整关替换文件。SMMO名称仍按SSTG内嵌引用读取，不重命名所有SMMO。
- 资源覆盖与兼容性范围见[身份和资源边界](拉米诺斯资源.md#kb-06-003-1)。

- SSTG 的逻辑标识与文件名分离：`0x69BAD0` 读取最后四个 XOR0x28 DWORDs，`0x40D5F8/0x669F00` 存储到 `manager+0x1FB0C..0x1FB18`，`0x403490/0x669F30` 复制给 `0x70DC10`。
- 比较使用隐藏获取器 `0x403D2D`、逻辑关卡 `0x41DF7A/0x7085D0`、逻辑副本 `0x41D1B5/0x7085F0` 和阶段 `0x418AF2/0x6772F0`。
- 入口8 要求逻辑身份 `0/100/7/0`；资源 ep22 超级脚本 `0/100/6/1` 仅适用于第七入口。

- 阶段错误检查 `0x70DDB9..0x70DE1E`：`0x669F30`返回的SSTG四元组末DWORD与`0x6772F0`读取的manager+0x1E540比较；不等时在`0x70DDDB`使用字符串`0xC70854`（`Open St Data File Error_%d_%d`），参数顺序是已读阶段／当前阶段，并转入错误状态9。
- `_0_1`是逻辑0≠1，不是文件共享错误码。
- CFEC另在`0x6F656E..0x6F657D`写入+0x2DA阶段，因此错误归因需包含入房及加载顺序。
- 上述CF78、阶段setter和错误检查区域与活动客户端逐字节一致；验证层级为静态消费字段和适配器构造，双人画面属于客户端联合验收范围。
